# Borrador LinkedIn — Hito 3 (ES)

> Puede publicarse solo o integrarse con uno posterior. Se conserva como registro.

Mi asistente de pedidos ya no pierde un pedido si el proceso se cae a la mitad.

Cada mensaje del cliente ahora es una transacción de PostgreSQL: estado, respuesta y pedido se guardan juntos o no se guarda nada. Los mensajes duplicados se descartan, y un "sí" repetido no crea un segundo pedido. Las respuestas pasan por un outbox con reintentos, así que una caída justo después de confirmar no pierde el mensaje. Si un cliente vuelve tres horas después, el bot pregunta antes de seguir; un día después, le ofrece el carrito anterior con precios actuales.

Lo que más me quedó no estuvo en el código que entregué. Mi fixture de tests borra la base de datos entre pruebas, y su puerto por defecto era el de otro proyecto corriendo en mi máquina. Un conflicto de puertos lo detuvo antes de que corriera nada. Ahora los tests usan una base aparte, y el fixture se niega a tocar cualquier base cuyo nombre no termine en `_test`. Una herramienta destructiva necesita su propia protección, no solo un valor por defecto correcto.

Resultado: 526 tests en verde, más 19 contra PostgreSQL real. El fake en memoria y la base real corren los mismos tests de contrato.

Lo que sigue: Telegram y el lado del restaurante en la conversación.
